DBML to SQL

Paste DBML and get CREATE TABLE SQL for PostgreSQL, MySQL, SQLite, SQL Server or Snowflake — with keys, defaults and foreign keys, and column types translated for the database you pick. You also get the diagram, so you can check the schema before you run anything.

At a glance

What it is
SQL to ER Diagram is a free, open-source browser tool that turns DBML into an interactive entity-relationship (ER) diagram.
Input
DBML (Database Markup Language) text.
Output
SQL CREATE TABLE statements for PostgreSQL, MySQL, SQLite, SQL Server or Snowflake, with column types translated, plus the interactive ER diagram.
Cost
Free. MIT-licensed open source. No account or signup.
Privacy
Runs entirely in your browser. The schema is never uploaded, and share links carry the diagram in the URL fragment, which is not sent to a server.
Limits
It never connects to your database itself: you paste schema text, or run one read-only catalog query in your own client and paste the result. There are no accounts, so there is no real-time multi-user editing; diagrams are kept in your browser, as a saved file, or as a share link. Layout stays smooth at around 300 tables.

How it works

  1. Paste your DBML (or drop a .dbml file on the page). DBML is detected automatically.
  2. Check the diagram: tables, keys and relations are drawn as they will be created.
  3. Open Export and choose a database under SQL for….
  4. Copy or download the SQL. Tables come first and foreign keys after, so the script runs in one pass.

Example

This DBML:

Enum plan {
  free
  pro
}

Table accounts {
  id integer [pk, increment]
  email varchar(255) [unique, not null]
  plan plan [default: 'free']
  settings jsonb
  created_at timestamp [default: `now()`]
}

Table projects {
  id integer [pk, increment]
  account_id integer [not null, ref: > accounts.id]
  name varchar(120) [not null]
  archived boolean [default: false]
}

…exports as this PostgreSQL:

-- PostgreSQL schema · generated by sqltoerdiagram.com

CREATE TYPE plan AS ENUM ('free', 'pro');

CREATE TABLE accounts (
  id serial PRIMARY KEY,
  email varchar(255) NOT NULL UNIQUE,
  plan plan DEFAULT 'free',
  settings jsonb,
  created_at timestamp DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE projects (
  id serial PRIMARY KEY,
  account_id integer NOT NULL,
  name varchar(120) NOT NULL,
  archived boolean DEFAULT false
);

ALTER TABLE projects ADD CONSTRAINT fk_projects_account_id FOREIGN KEY (account_id) REFERENCES accounts (id);

Pick MySQL instead and the enum becomes an enum(…) column, jsonb becomes json and boolean becomes tinyint(1); pick SQL Server and varchar becomes nvarchar. Try it with your own →

Guide

DBML is a good place to design a schema and a poor thing to hand a database: sooner or later you need real CREATE TABLE statements. This page gives you both views of the same DBML — the diagram, so you can see what you are about to create, and the SQL for the database you actually run.

How types are translated

DBML does not fix a type system: varchar, jsonb and my_custom_type are all just text to it. The converter recognises the common families and writes the target database's spelling:

  • Integers and auto-increment — integer, bigint, serial become int AUTO_INCREMENT on MySQL and int IDENTITY(1,1) on SQL Server.
  • Booleans — boolean becomes tinyint(1) on MySQL and bit on SQL Server.
  • Text — varchar(n) stays sized; unsized text becomes text, nvarchar(max) or VARCHAR as appropriate.
  • JSON, UUID, timestamps — jsonb becomes json on MySQL; uuid becomes char(36) or uniqueidentifier; timestamptz becomes datetimeoffset on SQL Server.

A type it does not recognise — a PostGIS geometry, an array, your own enum — is written exactly as you typed it, so nothing is silently changed into something wrong.

What to check before you run it

  • Enums are written the way each database supports them: a real type on PostgreSQL, enum(…) on MySQL, a CHECK constraint on SQLite and SQL Server, and plain text on Snowflake, which does not enforce CHECK.
  • A default of now() is written as CURRENT_TIMESTAMP, which all five databases accept. Other expression defaults are passed through as written, so check any that use database-specific functions.
  • SQLite gets every type as one of its five storage classes, and its foreign keys inside CREATE TABLE.
  • A foreign key that points at a table missing from the DBML is left out, and the missing table is listed under the editor.

Why use it

  • Private: everything runs in your browser — nothing is uploaded or stored on a server.
  • Five dialects: PostgreSQL, MySQL, SQLite, SQL Server and Snowflake from the same DBML.
  • Types translated: common types are mapped per database; a type it does not recognise is passed through unchanged rather than guessed.
  • Interactive: drag tables, auto-arrange, hide noise, add notes, and manually link columns.
  • Free & open source — no account, no sign-up.

FAQ

How do I convert DBML to SQL?

Paste the DBML into the editor, open Export and pick a database under “SQL for…”. You get CREATE TABLE statements followed by the foreign keys as ALTER TABLE … ADD CONSTRAINT.

Which databases can it generate SQL for?

PostgreSQL, MySQL, SQLite, SQL Server and Snowflake. For SQLite the foreign keys are written inside CREATE TABLE, because SQLite cannot add them afterwards.

What happens to DBML enums, notes and indexes?

They are carried into the SQL. An enum becomes CREATE TYPE … AS ENUM on PostgreSQL, enum(…) on MySQL and a CHECK constraint on SQLite and SQL Server. Indexes become CREATE INDEX. Notes become COMMENT ON statements on PostgreSQL and Snowflake and inline COMMENTs on MySQL; SQLite and SQL Server have no standard comment syntax, so notes are left out there.

Can I go the other way, from SQL to DBML?

Yes — see SQL to DBML. That direction keeps enums, defaults, notes and indexes.

Is my schema uploaded anywhere?

No. Everything runs locally in your browser — your schema is never uploaded to or stored on any server.

Is it free?

Yes. It is completely free and open source, with no account or sign-up required.
